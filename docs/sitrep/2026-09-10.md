- **The planner's output shape is now validated against a schema, and the
  model's output schema is exposed as a public function other code can
  call** (epic E9, 5 of 6 items done). Landed this session in pull request
  #2 (a set of proposed code changes reviewed and merged into the main
  line of the project): the model's expected-output schema became a
  documented public function, and a specific class of connection failure
  — a model endpoint rejecting the "give me structured JSON back" request
  outright — now gets automatically retried with a looser request instead
  of failing the whole task. One item remains open, listed below.
- **A subtle Chrome-automation trap is now documented and has a regression
  test guarding it** (epic E10). The trap: whichever piece of code first
  talks to a given browser tab "owns" that tab for its whole life, and
  wrapping that connection in a timeout and later cancelling the timeout —
  even after a successful call — silently kills the tab for every later
  call. This bit the project's own earlier work at least once. Landed in
  pull request #2 alongside E9.
- **The MCP server itself is built, merged, and independently
  re-verified** (epic E11, this session's actual ask, all 12 items done).
  `cmd/ferro-mcp` is a new program that speaks MCP (the protocol AI agents
  use to call out to external tools) and drives one real, persistent
  Chrome profile — the one you sign into by hand once. Specifically:
  - Any number of your Claude Code sessions can point at the same server
    at once. The first one to start "wins" and is the only one that
    actually opens Chrome (internally: it wins an exclusive lock on a
    file, which is how it knows it's first); every other session talks to
    that first one over a local socket instead of opening its own Chrome,
    so you never get Chrome fighting itself over one profile.
  - Nothing the server does is silently a free-for-all against your
    accounts. It reads a plain JSON allow-list of origins (like
    `https://mail.google.com`) you edit by hand, and refuses to touch or
    even read a page whose origin isn't on the list — this is the
    guardrail against a malicious or confused web page trying to trick an
    agent into acting on your live, logged-in session.
  - It exposes both a single "just do this goal" tool and the smaller
    building-block actions (navigate, click, fill in a field, and so on)
    individually, so an agent can either hand it a whole task or drive it
    step by step.
  - This was reviewed line by line (every new file read directly, not
    summarized by the agent that wrote it) and re-tested from scratch
    against real Chrome after merging — build, formatting, static
    analysis, and the full test suite, including all 16 individually
    named tests, all passed. A follow-up pull request (#4) then fixed two
    bookkeeping gaps the review caught: the plan file's checkboxes for
    this epic hadn't been ticked off despite the work landing, and one
    task's note cited a test name that doesn't exist in the codebase (the
    actual, correct test was found and cited instead).
  - The one-off prototype version of this server that predated this
    session's work, and its throwaway branch, are both deleted — but only
    after confirming every piece of unique value in them (two real bug
    fixes it had found) was actually carried over into the real version
    first.

## Risks & watch items

- **The project's headline efficiency claim hasn't been measured against a
  real model yet.** ferro's whole pitch is that it asks the model for a
  plan once and then runs that plan deterministically, instead of the
  model being consulted on every single step the way most browser-agent
  tools work. That claim is currently backed by design reasoning and
  token-count math in the project's design document, not by an actual
  benchmark run — the task to do that (measuring plan validity against a
  real 7-to-14B-parameter model, and proving a repeated task costs zero
  extra model calls) is one of the four unscoped items above. This isn't
  urgent, but it's worth knowing the headline claim is currently
  design-level, not measured.
- **The new MCP server is a new, real security boundary that hasn't been
  used in anger yet.** It exists specifically to let outside agents act
  inside your logged-in browser sessions, gated only by a plain-text
  allow-list file you maintain by hand. The design and the automated tests
  both check out, but there's no red-team or adversarial pass on it yet —
  worth a quick real-world trial (pointing an agent at one allow-listed
  site and watching what it actually does) before trusting it broadly.

## Glossary for this report

- **MCP (Model Context Protocol)**: the standard protocol that lets AI
  coding agents (like Claude Code) call out to external tools.
- **ferro-mcp**: the new program this session built — an MCP server that
  drives one real, signed-in Chrome browser profile on your behalf.
- **Epic**: one named phase of work in the project's plan, made up of
  several smaller tasks.
- **Pull request (PR)**: a proposed set of code changes, reviewed and then
  merged into the project's main line of code.
- **Allow-list**: the plain-text file of web addresses the MCP server is
  permitted to act against; anything not listed is refused by default.
- **Owner / shim**: the leader-election pattern the server uses so multiple
  sessions can share one Chrome profile — the first session to start
  becomes the "owner" and actually opens Chrome; every other session
  becomes a "shim" that relays its requests to the owner instead of
  opening its own Chrome.
